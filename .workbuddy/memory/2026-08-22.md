## v1.1 修复（13:25）

**用户问题**：网页预览显示的 Comment 是 `Res2`、`LED0` 这种库引用名，**不是 AD 里实际显示的 Comment**（5.1K、红）。

**双 bug 定位**：
1. `build_comment_designator_map` 硬假设 "偶数 idx=Comment, 奇数 idx=Designator"，但 **type-c 转接板用布局 B**：idx 0 是 PCB 全局注释（"按照黑色油墨生产"），之后 (Comment, Designator) 对**Comment 在奇数、Designator 在偶数**，末尾混 PCB 尺寸和网络名（VBUS/GND/D+/D-/CC1/CC2/20mm/15mm）
2. `find_widestrings_offset` 只走普通 FAT，但 WideStrings6 只有 472 字节（< minisectorcutoff 4096B），走 **mini-FAT** 存放在 mini-stream 容器中，普通 FAT 算出偏移 128000 但实际物理偏移 3056（差 124944 字节）
3. olefile `openstream().read()` 跨 mini-stream 容器扇区读多 24 字节（容器的下一个流的扇区内容）

**修复方案**：
- `build_comment_designator_map(ws_entries, designators)` 改**反查模式**：Components6 的 SOURCEDESIGNATOR 是权威位号集合，在 WideStrings6 中搜索每个 designator，Comment 永远是它的"前一条"
- `find_widestrings_offset` 改用**内容 magic 搜索**：用 olefile 读 WideStrings6 内容，在 raw_file 字节里搜匹配来定位物理偏移；size 用 direntry.size（逻辑大小）
- 兼容 `Res2`（库引用名 vs 真实 Comment）的常见混淆——若反查仍然失败就 fallback 到 SOURCELIBREFERENCE，但反查逻辑正确时 0 fallback

**关键数据点**：
- type-c转接板.PcbDoc WideStrings6: 472B, mini-FAT, 13 字符串 + 14 PCB 装饰符
- 真实 Comment（WideStrings6）: R1/R2/R3=5.1K, D1=红, P1=TYPE-C, P2=Header 6
- 库引用名（SOURCELIBREFERENCE）: R* = Res2, D1 = LED0, P1 = TYPE-C, P2 = Header 6
- 注意 P1/P2 库引用名跟真实 Comment 同名，导致 fallback 时"碰巧"显示正确——这是为什么 bug 一直没被发现的根本原因

## Bug 修复 — WideStrings6 布局差异 + mini-FAT 支持（用户测试发现）

**触发**：用户测试 `type-c转接板.PcbDoc`（桌面文件），预览全部显示库引用（SOURCELIBREFERENCE），脱敏清除 0 条。

**根因（双重）**：
1. `build_comment_designator_map` 假设"偶数索引=Comment，奇数索引=Designator"，但 WideStrings6 实际存在两种布局：
   - 布局A（旧文件）：从 idx 0 开始严格 (Comment, Des) 交替
   - 布局B（新文件）：idx 0 是 PCB 全局注释（如"按照黑色油墨生产"），之后 (Comment, Des) 对 Comment 在奇数位、Des 在偶数位
   - 部分文件末尾还混入尺寸/网络名字符串
2. `find_widestrings_offset` 只支持普通 FAT 流（>= 4096 字节），但 WideStrings6 < 4096 字节时走 mini-FAT（存放在 Root Entry 的 mini-stream 容器里），旧实现会算错偏移
3. olefile 的 `openstream().read()` 返回的 ws_data 可能跨扇区包含下一个流的数据（mini-stream 容器扇区对齐），需用 `direntry.size` 作为真实逻辑大小

**修复**：
1. `build_comment_designator_map(ws_entries, designators)` 改为反查模式：用 Components6 的 SOURCEDESIGNATOR 作为权威位号集合，在 WideStrings6 里扫描匹配，匹配到的"前一条"就是 Comment（两种布局通用）
2. `find_widestrings_offset` 改用内容 magic 搜索定位物理偏移 + 返回 `(ws_offset, ws_size)` 元组，用 `direntry.size` 作为 ws_size
3. `clear_all_comments` / `set_comment` 都加了 `designators` 参数

**回归验证**：
- type-c转接板.PcbDoc (mini-FAT 472 字节, 布局B): 6 条清除、6 条回填成功，Round-trip 100% 一致
- 新执行器202608.PcbDoc (普通 FAT 4592 字节, 布局A): 110 条清除、4 条回填成功，无回退

**打包注意事项**：
- 重新打包前必须先清掉 `__pycache__/` 和 `*.pyc`，否则 PyInstaller 可能打包进旧的冻结字节码（曾导致新 EXE 仍跑旧逻辑）
- 旧 EXE 文件被占用时用 PowerShell `Stop-Process -Id <PID> -Force` 杀进程后用 `rm -f` 删除

## v1.3 修复（13:42）

**问题1 用户测试**：用 mkf201912-V2026.PcbDoc 跑脱敏，BOM 显示所有 Comment 都清空，但 **Inductor L1 的 Comment 还是 4.7uH**。

**问题2 用户测试**：脱敏完成后下载 PcbDoc，360 浏览器报"无法从网站上提取文件"。

**根因 1（脱敏漏元件）**：`build_comment_designator_map` 用 dict 存 `mapping[designator] = {...}`。当 WideStrings6 中**同一位号字符串出现多次**（Altium 在元件描述/网络组区复用位号文本），dict 会被覆盖。本案中 `L1` 在 ws 流里出现 2 次：第一次 prev='4.7uH'（真正的 Comment），第二次 prev='N'（网络名）。第二次写入 dict 时覆盖了第一次，导致 map['L1'] 指向 'N'，clear 时清掉的是网络名而真正的 Comment 区保留。

**根因 2（下载失败）**：Werkzeug 自动生成的 Content-Disposition 同时含 `filename=`（中文段被替换成 `_`）和 `filename*=UTF-8''...`（RFC 5987 扩展）。360 浏览器对这种双字段解析异常。

**修复**：
1. `pcb_tool/pcb_binary.py`：`build_comment_designator_map` 返回值改 `{text: list[entry]}`（取代 `{text: entry}`），用 setdefault 收集同名位号的所有 prev 候选；`clear_all_comments` 遍历 list 中每个候选全清；`set_comment` 用 list 第一个匹配；`get_pcb_info` 取第一个匹配的 comment_entry.text 显示。`Dict` 加入 typing import
2. `pcb_tool/pcb_processor.py`：输出文件名 `_脱敏_` → `_desensitized_`，`_已回填_` → `_refilled_`（去掉中文，避开 360 解析问题）
3. `static/app.js`：新增 `setupDownloadButton()` 和 `downloadViaBlob()`，下载按钮改用 fetch + Blob + objectURL 触发，绕开服务端 Content-Disposition

**验证数据**：

**修正之前的误判**：v1.3 记录的"_set_comment 长度校验误报"实际不是误报。实测 R1 buffer strlen=6（'1K'4B + null 2B），strlen 本来就含 null 终止符，与 new_bytes 口径一致。BOM 值比原 Comment 长时确实无法原地写入（受 OLE 流定长约束），属真实容量限制。失败提示已改为"新值 N 字符超过原 Comment 容量 M 字符"更明确。

**修复的真实 bug（2 个）**：

**注意**：验证脚本取文件别用 `sorted(glob)[-1]`（字典序 `_desensitized_` < `_refilled_` 会取错旧文件），用 `max(files, key=os.path.getmtime)`。

## v1.5 修复：PCB 封装名中文乱码 + 回填面板 PCB 文件名不显示（14:0x）

**用户反馈**：回填完成后审计报告的"封装"列对部分元件显示乱码（如 C1 显示 `6*7◆◆◆◆`），且回填面板拖入 PCB 文件后文件名不显示（只有 BOM 显示）。

**根因 1（封装列乱码）**：`pcb_binary.parse_components` 整个记录用 `decode('ascii', errors='replace')` 解码。但 Altium Designer **简体中文版** 在 PATTERN/Comment 等值字段写入的是 **GBK 编码**（不是 UTF-8），所以中文封装名如"插件"、"带散热"、"直" 全部被替换成 U+FFFD '◆'。诊断命令：
```python
m = re.search(rb'PATTERN=([^\x00|]*)', rec)
raw = m.group(1)  # C1: b'6*7\xb2\xe5\xbc\xfe' → '6*7插件' (GBK)
```

**根因 2（PCB 文件名不显示）**：`app.js` 的 `onPcbSelected` 用 `$('#filename-${panelId}')` 找文件名 span。回填面板 panelId='fill'，算出 selector='#filename-fill'，但 HTML 实际 id 是 `#filename-pcb-fill`（在 `#files-summary-fill` 摘要块里），所以 PCB 选中后这个 span 永远没被填充。

**修复**：
1. `pcb_tool/pcb_binary.py` `parse_components`：record 整体改 `decode('gbk', errors='replace')`，GBK 兼容 ASCII 不会影响纯英文键名
2. `static/app.js` `onPcbSelected`：分支处理——fill 面板用 `#filename-pcb-fill`，desensitize 面板用 `#filename-desensitize`

**验证**（新执行器202608.PcbDoc）：
| 位号 | 修复前 pattern | 修复后 pattern |
|------|---------------|---------------|
| C1 | `6*7����` | `6*7插件` |
| J1 | `XH2.54-2PIN??` | `XH2.54-2PIN直` |
| U4 | `SOP-8??????` | `SOP-8带散热` |
| C2/C5 | `0805-C` | `0805-C`（纯 ASCII 不变）|

**教训**：解析 Altium 二进制时，所有用户级字符串字段（PATTERN、Comment）都要用 GBK 尝试解码；不要无脑 ASCII。
